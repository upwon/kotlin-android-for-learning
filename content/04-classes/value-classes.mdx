`value class`（旧名 inline class）解决一个 Java 里没法解决的问题：
**给基本类型套上语义，但不付出对象开销**。

## 1. 问题：String 太万能了

```kt
fun transfer(fromUserId: String, toUserId: String, orderId: String) { }

// 调用时参数顺序搞反，编译器一句话都不说
transfer(orderId, fromUserId, toUserId)    // 😱 编译通过，线上事故
```

用 `value class` 让类型系统帮你检查：

```kotlin
@JvmInline
value class UserId(val value: String)

@JvmInline
value class OrderId(val value: String)

fun transfer(from: UserId, to: UserId, order: OrderId) =
    "从 ${from.value} 转给 ${to.value}，订单 ${order.value}"

fun main() {
    val a = UserId("u1")
    val b = UserId("u2")
    val o = OrderId("o1")

    println(transfer(a, b, o))
    // println(transfer(o, a, b))   // ❌ 编译错误，类型不匹配
}
```

## 2. 零成本在哪里

```kt
@JvmInline
value class UserId(val value: String)

fun load(id: UserId) { }

// 编译后大致等价于：
fun load(id: String) { }        // UserId 消失了，直接传 String
```

<Callout type="success">

运行时**没有 UserId 对象**——编译器把它擦除成了底层类型。
所以你既拿到了编译期的类型安全，又没有额外的堆分配。

这是普通的包装类（`class UserId(val value: String)`）做不到的：那会真的创建对象。

</Callout>

## 3. 规则

```kotlin
@JvmInline
value class Password(val value: String) {
    // ✅ 可以有属性（但不能有幕后字段）
    val masked: String get() = "*".repeat(value.length)

    // ✅ 可以有方法
    fun isStrong(): Boolean = value.length >= 8

    // ✅ 可以有 init 块做校验
    init {
        require(value.isNotBlank()) { "密码不能为空" }
    }
}

fun main() {
    val p = Password("secret123")
    println(p.masked)
    println(p.isStrong())
    println(runCatching { Password("") }.exceptionOrNull()?.message)
}
```

限制清单：

- **有且仅有一个**主构造函数属性，必须是 `val`
- 不能有幕后字段（只能是计算属性）
- 不能继承类，也不能被继承（隐式 final）
- **可以实现接口**

```kotlin
interface Printable {
    fun print(): String
}

@JvmInline
value class Money(val cents: Int) : Printable {
    override fun print() = "¥%.2f".format(cents / 100.0)

    operator fun plus(other: Money) = Money(cents + other.cents)
}

fun main() {
    val a = Money(1250)
    val b = Money(340)
    println((a + b).print())
}
```

## 4. 什么时候会被迫装箱

这是必须知道的部分：

```kotlin
@JvmInline
value class UserId(val value: String)

fun direct(id: UserId) = id.value            // ✅ 不装箱

fun generic(list: List<UserId>) = list.size  // ⚠️ 泛型 → 装箱
fun nullable(id: UserId?) = id?.value        // ⚠️ 可空 → 装箱

interface Handler { fun handle(id: UserId) } // ⚠️ 接口方法 → 装箱

fun main() {
    println(direct(UserId("u1")))
    println(generic(listOf(UserId("u1"))))
    println(nullable(null))
}
```

<Callout type="warn" title="三种装箱场景">

| 场景 | 是否装箱 | 原因 |
| --- | --- | --- |
| 直接作为参数/返回值 | ❌ 不装箱 | 直接用底层类型 |
| 作为泛型参数 `List<UserId>` | ✅ 装箱 | JVM 泛型需要对象 |
| 可空类型 `UserId?` | ✅ 装箱 | 底层类型可能是 primitive，没有 null |
| 作为接口的实现类型 | ✅ 装箱 | 多态分派需要真实对象 |

即使装箱了，`value class` 也不比普通包装类差——只是**没有额外收益**。
所以别为了「避免装箱」把代码写扭曲，类型安全本身就值回票价了。

</Callout>

## 5. 与 Java 互操作

```kt
@JvmInline
value class UserId(val value: String)

fun load(id: UserId) { }
```

Kotlin 编译器会给这个函数的名字加上 hash 后缀（比如 `load-hXsQ8Yg`），
防止签名冲突——因为擦除后 `load(UserId)` 和 `load(String)` 长得一样。

<Callout type="warn">

后果：**Java 侧几乎没法调用参数是 `value class` 的函数。**

如果某个 API 需要被 Java 调用，要么别用 `value class`，
要么加 `@JvmName` 手动指定一个干净的名字（但那样又会有签名冲突风险）。

Android 混合工程里，`value class` 适合用在**纯 Kotlin 的内部代码**中。

</Callout>

## 6. Android 实战

```kt
// 1. 区分同为 String 的 ID
@JvmInline value class UserId(val value: String)
@JvmInline value class ProductId(val value: String)

// 2. 带单位的数值，避免 px/dp 混用
@JvmInline value class Dp(val value: Float)
@JvmInline value class Px(val value: Int)

fun Dp.toPx(density: Float) = Px((value * density).toInt())

// 3. 领域约束
@JvmInline
value class Email(val value: String) {
    init { require("@" in value) { "邮箱格式不对：$value" } }
}

// 4. 类型安全的资源 ID
@JvmInline value class LayoutRes(@androidx.annotation.LayoutRes val id: Int)
```

<Callout type="tip">

Jetpack Compose 里 `Dp`、`Sp`、`Color` 全都是 `value class`——
这正是它能做到「类型安全 + 零开销」的原因。
`16.dp` 在运行时就是一个 `Float`，没有任何包装对象。

</Callout>

<Callout type="warn" title="别过度使用">

每个 `value class` 都是一层需要理解的间接。判断标准：

- ✅ **这个值容易和同类型的其他值搞混**（多个 String ID、px vs dp）
- ✅ **这个值有领域约束**（Email 必须含 @）
- ❌ 只是想给类型起个别名 → 用 `typealias`（零成本，但**没有类型检查**）
- ❌ 这个值只在一个函数内部流转 → 不值得

`typealias` 和 `value class` 的区别很关键：

```kotlin
typealias UserName = String            // 只是别名，String 和 UserName 完全互通

@JvmInline
value class UserId(val value: String)  // 真正的新类型，不能和 String 混用

fun main() {
    val n: UserName = "abc"
    val s: String = n                  // ✅ typealias 没有类型检查
    println(s)

    val id = UserId("u1")
    // val s2: String = id             // ❌ value class 有类型检查
    println(id.value)
}
```

</Callout>

## 练习

<Quiz
  index={1}
  question={
    <>
      <code>@JvmInline value class UserId(val value: String)</code> 在运行时是什么？
    </>
  }
  options={[
    '一个 UserId 对象',
    '大多数情况下就是一个 String，UserId 被编译器擦除了',
    '一个包含 String 字段的包装对象',
    '一个 int 句柄',
  ]}
  answer={1}
>

大多数情况下**就是底层的 String**——`value class` 在编译期被擦除，
运行时没有对应的对象，也就没有额外的堆分配。

这正是它相对普通包装类的价值：编译期有完整的类型检查，运行时零开销。

「大多数情况」是因为有三种例外会触发装箱：作为泛型参数（`List<UserId>`）、
作为可空类型（`UserId?`）、作为接口的实现类型。

</Quiz>

<Quiz
  index={2}
  question={
    <>
      <code>typealias UserName = String</code> 和 <code>value class UserId(val value: String)</code> 的关键区别？
    </>
  }
  options={[
    '没有区别',
    'typealias 只是别名，和 String 完全互通；value class 是真正的新类型，有编译期检查',
    'typealias 性能更差',
    'value class 不能有方法',
  ]}
  answer={1}
>

`typealias` 纯粹是**换个名字**——`UserName` 和 `String` 在类型系统里是同一个东西，
可以随意互相赋值，起不到任何防混淆作用。

`value class` 创建了一个**真正的新类型**：`UserId` 不能赋给 `String`，
把参数顺序写反会编译报错。

选择依据：只想让长泛型签名短一点（`typealias Handler = (Int, String) -> Unit`）
用 typealias；想让编译器帮你区分同底层类型的不同语义，用 value class。

</Quiz>

<Quiz
  index={3}
  type="multi"
  question="以下哪些情况会导致 value class 装箱？"
  options={[
    '作为函数参数直接传递',
    '放进 List<UserId>',
    '声明为可空类型 UserId?',
    '作为接口方法的参数类型',
  ]}
  answer={[1, 2, 3]}
>

B、C、D 都会装箱：

- **泛型**：JVM 泛型只能持有对象，无法存储擦除后的 primitive/原始值
- **可空**：底层类型可能是 primitive（比如 `value class Money(val cents: Int)`），
  primitive 没有 null，只能装箱
- **接口**：多态分派需要一个真实的对象来承载虚方法表

A 是最典型的**不装箱**场景——直接传参、直接返回时，编译器直接用底层类型。

即使装箱了也不亏：那只是退化成了普通包装类的水平，类型安全的收益仍在。
别为了避免装箱把代码写扭曲。

</Quiz>

<Quiz
  index={4}
  question="value class 在和 Java 互操作时的主要问题是什么？"
  options={[
    'Java 完全看不到 value class',
    '函数名会被加上 hash 后缀防止签名冲突，导致 Java 侧几乎无法调用',
    'value class 会导致 Java 编译变慢',
    '没有问题',
  ]}
  answer={1}
>

因为擦除后 `fun load(id: UserId)` 和 `fun load(id: String)` 的 JVM 签名完全一样，
编译器必须给前者加 hash 后缀（如 `load-hXsQ8Yg`）来避免冲突。

结果就是 Java 侧看到一个名字很怪的方法，实际上没法正常调用。

实践建议：`value class` 用在**纯 Kotlin 的内部代码**里。
会被 Java 调用的公开 API 边界上避免使用，或者提供一个接收底层类型的重载。

</Quiz>
