这一章不教语法，只解决一件事：**让你的 Android 工程用上对的 Kotlin 版本，并且知道每个开关在调什么。**
如果你已经在维护一个 Kotlin 化的 Android 项目，可以只看「版本对齐」和「kapt 还是 KSP」两节。

## 版本对齐：三个数字要看懂

Android 工程里跟 Kotlin 相关的版本有三层，经常被混为一谈：

| 版本 | 在哪写 | 管什么 |
| --- | --- | --- |
| Kotlin Gradle Plugin | `plugins { kotlin("android") version "..." }` | 用哪个版本的 Kotlin 编译器 |
| `jvmTarget` | `compilerOptions { jvmTarget }` | 编出来的字节码给哪个 JVM 版本用 |
| `languageVersion` / `apiVersion` | `compilerOptions` | 允许用哪些语言特性 / 标准库 API |

典型的模块级 `build.gradle.kts`：

```kt
plugins {
    id("com.android.application")
    id("org.jetbrains.kotlin.android") version "2.1.21"
}

kotlin {
    compilerOptions {
        jvmTarget.set(JvmTarget.JVM_17)

        // 把警告当错误，团队项目里建议开
        allWarningsAsErrors.set(false)

        // opt-in 实验性 API 时用，避免每个文件手写 @OptIn
        freeCompilerArgs.add("-opt-in=kotlin.RequiresOptIn")
    }
}
```

<Callout type="warn" title="jvmTarget 必须和 Java 的 targetCompatibility 一致">

Android 工程里 Java 和 Kotlin 是两条编译链，各自有各自的目标版本设置。两边不一致时
Gradle 会直接报 `Inconsistent JVM-target compatibility detected`。

```kt
android {
    compileOptions {
        sourceCompatibility = JavaVersion.VERSION_17
        targetCompatibility = JavaVersion.VERSION_17   // ← 这个
    }
}

kotlin {
    compilerOptions {
        jvmTarget.set(JvmTarget.JVM_17)                // ← 要和上面一致
    }
}
```

更省心的写法是用 **toolchain** 一次性钉死两边：

```kt
kotlin {
    jvmToolchain(17)
}
```

</Callout>

## kapt 还是 KSP

这是 Android 工程里唯一值得你花时间做的决策，因为它直接决定编译速度。

- **kapt**（Kotlin Annotation Processing Tool）：为了复用 Java 的注解处理器而生。
  它需要先把 Kotlin 代码生成 **Java stub**，再交给 javac 跑处理器——stub 生成这一步很慢，
  而且会让增量编译大面积失效。
- **KSP**（Kotlin Symbol Processing）：直接读 Kotlin 的符号信息，不生成 stub。
  官方数据是**快约 2 倍**，实际大项目上体感差距更大。

<Callout type="success">

**结论：新代码一律用 KSP。** Room、Moshi、Hilt（2.44+）、Glide 都已经有 KSP 版本。
只有当某个库确实还没提供 KSP 处理器时，才为它保留 kapt。

</Callout>

```kt
plugins {
    id("com.google.devtools.ksp") version "2.1.21-2.0.1"
}

dependencies {
    implementation("androidx.room:room-runtime:2.6.1")
    ksp("androidx.room:room-compiler:2.6.1")     // 以前是 kapt(...)
}
```

注意 KSP 的版本号是 `<Kotlin 版本>-<KSP 版本>` 的形式，**前半段必须和你的 Kotlin 版本完全一致**，
升 Kotlin 时这一行也得跟着改。

## 和 Java 共存

Android 项目不需要一次性全量迁移。Kotlin 和 Java 可以在同一个 module 里逐文件共存，
互相调用几乎无感——Android Studio 的 `Code → Convert Java File to Kotlin File`
（`Ctrl+Alt+Shift+K`）可以单文件转换。

<Callout type="warn" title="自动转换的结果一定要人工过一遍">

转换器最容易在两个地方产出「能编译但不好」的代码：

1. **满屏的 `!!`**。因为 Java 侧没有可空性注解，转换器只能假设一切非空。
   这些 `!!` 应该逐个改成 `?.`、`?:` 或者干脆把类型声明成可空的。
2. **该用 `val` 的地方全是 `var`**。转换器保守地保留了可变性。

换句话说：自动转换给你的是「语法是 Kotlin 的 Java 代码」，把它改成真正的 Kotlin 是你的事。

</Callout>

## 做实验的三个地方

学语法时你需要一个能快速跑一小段代码的地方，**不要为此新建 Android 工程**：

1. **本站的代码块** —— 最快，直接改直接跑，不用装任何东西。
2. **Scratch File**（`Ctrl+Alt+Shift+Insert` → Kotlin）—— Android Studio 里的临时文件，
   不属于任何 module，写完立刻能跑，还能看到每行的求值结果。
3. **Kotlin REPL** —— `Tools → Kotlin → Kotlin REPL`，适合试单行表达式。

<Callout type="tip">

Scratch File 是被严重低估的功能。它能勾选 "Use classpath of module"，
这样你可以在里面直接调用**工程里的真实类**做实验，比写一堆临时的单元测试快得多。

</Callout>

## 一段能跑的代码

确认环境好了之后，先跑通这个——它同时用到了顶层函数、字符串模板和集合操作，
这三样是后面每一章的基础：

```kotlin
fun main() {
    val versions = mapOf(
        "Kotlin" to "2.1.21",
        "AGP" to "8.7.0",
        "KSP" to "2.1.21-2.0.1",
    )

    versions.forEach { (name, version) ->
        println("$name 版本：$version")
    }

    val latest = versions.keys.sorted().joinToString(" / ")
    println("按字母序：$latest")
}
```

Android 工程里 Java 和 Kotlin 是两条独立的编译链，各有各的目标 JVM 版本设置。
两边不一致时 Gradle 会拒绝构建。

修法要么是把两处显式改成同一个值，要么更省事——用 `kotlin { jvmToolchain(17) }`
一次性钉死两边。

</Quiz>

<Quiz
  index={2}
  question="为什么 KSP 比 kapt 快？"
  options={[
    'KSP 用多线程并行处理注解',
    'KSP 直接读 Kotlin 符号信息，不需要先生成 Java stub',
    'KSP 把注解处理挪到了运行时',
    'KSP 会缓存上一次的处理结果，kapt 不会',
  ]}
  answer={1}
>

kapt 的设计目标是**复用现有的 Java 注解处理器**，所以它必须先把 Kotlin 代码转成
Java stub 再交给 javac。这一步既慢，又会让增量编译大面积失效。

KSP 是为 Kotlin 重新设计的 API，直接消费编译器的符号信息，跳过了整个 stub 环节。

</Quiz>

<Quiz
  index={3}
  type="multi"
  question="用 Android Studio 把一个 Java 文件自动转成 Kotlin 后，通常需要人工修正哪些地方？"
  options={[

    '本该是 val 却被保留成 var 的变量',

    '包名需要手动改成小写',
  ]}
  answer={[0, 1]}

前两项是自动转换最典型的产出问题：

- Java 侧缺少可空性注解，转换器只能假设一切非空，于是塞满 `!!`。这些应该按实际语义改成
  `?.`、`?:`，或者把类型直接声明为可空。
- 转换器保守地把所有变量都保留为 `var`，需要你判断哪些其实是只读的。

C、D 是错的：`for` 循环在 Kotlin 里完全合法、有时比 `forEach` 更合适；包名规则两边一样。

</Quiz>
