Kotlin 集合最重要的设计是**在类型层面区分只读和可变**——`List` 和 `MutableList`
是两个接口。但这个区分有个必须理解的边界：**只读不等于不可变**。

## 1. 只读接口 vs 可变接口

```kotlin
fun main() {
    val readOnly: List<String> = listOf("a", "b")
    val mutable: MutableList<String> = mutableListOf("a", "b")

    // readOnly.add("c")      // ❌ List 没有 add
    mutable.add("c")          // ✅

    println(readOnly)
    println(mutable)
}
```

层级关系：

```
Collection<out E>          ← 只读
├── List<out E>            ← 只读，有序，可索引
├── Set<out E>             ← 只读，不重复
└── MutableCollection<E>   ← 可变
    ├── MutableList<E>
    └── MutableSet<E>

Map<K, out V>              ← 只读（注意 Map 不是 Collection）
└── MutableMap<K, V>
```

<Callout type="java" title="Java 只有一套接口">

Java 的 `List` 既有 `get` 也有 `add`。想要只读，只能用
`Collections.unmodifiableList(...)` 包一层——**编译期没有任何提示**，
调用 `add` 要到运行时才抛 `UnsupportedOperationException`。

Kotlin 把这个约束提到了类型层面：函数签名写 `List<T>` 就是在说
「我不会改这个集合」，调用方一眼可见。

</Callout>

## 2. 只读 ≠ 不可变

这是必须理解的边界：

```kotlin
fun main() {
    val mutable = mutableListOf("a", "b")
    val readOnlyView: List<String> = mutable    // 只是换了个类型看它

    mutable.add("c")
    println(readOnlyView)      // [a, b, c] ⚠️ 跟着变了

    // 而且能强转回去
    @Suppress("UNCHECKED_CAST")
    (readOnlyView as MutableList<String>).add("d")
    println(mutable)           // [a, b, c, d]
}
```

<Callout type="warn">

`List` 是一个**只读视图**，不是不可变集合。它保证的是「**通过这个引用**改不了」，
不保证「没有别人能改」。

真正需要不可变时：

```kt
// 1. 返回副本
val snapshot: List<String> = mutable.toList()     // 独立的新集合

// 2. 用 kotlinx.collections.immutable（第三方）
val truly: PersistentList<String> = persistentListOf("a", "b")
```

Compose 里这一点很重要——传给 `@Composable` 的 `List` 如果背后是可变的，
Compose 无法正确判断是否需要重组，会导致漏刷新或过度重组。
所以 Compose 推荐用 `ImmutableList`。

</Callout>

## 3. 构造集合

```kotlin
fun main() {
    // 基本构造
    println(listOf(1, 2, 3))
    println(mutableListOf(1, 2))
    println(setOf(1, 2, 2, 3))            // 自动去重
    println(mapOf("a" to 1, "b" to 2))

    // 空集合
    println(emptyList<Int>())
    println(listOfNotNull(1, null, 3))    // 过滤掉 null

    // 带初始化 lambda
    println(List(5) { it * it })
    println(MutableList(3) { "item$it" })

    // builder 风格（1.6+）
    val built = buildList {
        add("a")
        addAll(listOf("b", "c"))
        if (true) add("d")
    }
    println(built)

    println(buildMap {
        put("x", 1)
        putAll(mapOf("y" to 2))
    })
}
```

<Callout type="tip">

`buildList` / `buildSet` / `buildMap` 的好处：**在 lambda 内部是可变的，
返回出来是只读的**。避免了「先建 mutableListOf、最后 toList()」的两步走，
也避免了把可变引用暴露出去。

需要条件性地添加元素时，它比 `listOfNotNull` + 一堆 `takeIf` 清楚得多。

</Callout>

## 4. 具体实现类

```kotlin
fun main() {
    // listOf 返回的实际类型
    println(listOf(1, 2, 3).javaClass.simpleName)      // ArrayList（的包装）
    println(mutableListOf(1).javaClass.simpleName)     // ArrayList
    println(setOf(1).javaClass.simpleName)             // LinkedHashSet
    println(mapOf("a" to 1).javaClass.simpleName)      // LinkedHashMap

    // 需要特定实现时显式指定
    val linked = LinkedHashSet<Int>()
    val sorted = sortedSetOf(3, 1, 2)
    val hash = hashMapOf("a" to 1)
    println("$sorted")
}
```

<Callout type="warn">

注意 `setOf` / `mapOf` 默认返回 **LinkedHashSet / LinkedHashMap**——
它们**保持插入顺序**。这和 Java 的 `HashSet` / `HashMap` 不同。

好处是行为可预测（迭代顺序稳定），代价是略多一点内存。
明确不需要顺序且在意内存时用 `hashSetOf` / `hashMapOf`。

</Callout>

## 5. 集合的型变

```kotlin
fun printAll(items: List<Any>) = println(items)

fun addTo(items: MutableList<Any>) { items.add(1) }

fun main() {
    val strings: List<String> = listOf("a", "b")
    printAll(strings)            // ✅ List<out E> 是协变的

    val mutableStrings: MutableList<String> = mutableListOf("a")
    // addTo(mutableStrings)     // ❌ MutableList<E> 不变
}
```

- `List<out E>` —— **协变**，`List<String>` 可以当 `List<Any>` 用（只读安全）
- `MutableList<E>` —— **不变**，因为能写入，协变会破坏类型安全

这是 [4.9 泛型](/docs/04-classes/generics)里 `out`/`in` 的最佳示例。

## 6. 与 Java 互操作

<Callout type="warn" title="Java 侧看到的都是可变集合">

```kt
// Kotlin
fun getNames(): List<String> = listOf("a", "b")
```

```java
// Java 侧
List<String> names = KtFileKt.getNames();
names.add("c");     // 编译通过！运行时抛 UnsupportedOperationException
```

Kotlin 的只读接口在字节码里就是 `java.util.List`——**Java 侧看不到只读约束**。

反过来，Java 返回的 `List` 在 Kotlin 侧是平台类型 `(Mutable)List<String>!`，
既能当只读用也能当可变用，编译器不管。

混合工程里，跨语言边界上的集合要格外小心。

</Callout>

## 7. Android 场景

```kt
class MyViewModel : ViewModel() {
    // 幕后属性模式：内部可变，外部只读
    private val _items = MutableStateFlow<List<Item>>(emptyList())
    val items: StateFlow<List<Item>> = _items.asStateFlow()

    fun add(item: Item) {
        _items.update { it + item }      // 生成新 List，触发 StateFlow 更新
    }
}
```

<Callout type="warn" title="StateFlow 靠 equals 判断是否更新">

```kt
// ❌ 原地修改 MutableList，引用没变，StateFlow 认为「没变化」，不发射
private val list = mutableListOf<Item>()
_state.value = list.apply { add(newItem) }    // UI 不刷新！

// ✅ 每次生成新的不可变 List
_items.update { current -> current + newItem }
```

`StateFlow` 会用 `equals` 做去重（conflation）。传同一个可变对象进去，
它看到的是「值没变」，直接丢弃这次更新。

**这是 Android 上「数据改了但 UI 不刷新」最常见的原因之一。**
集合状态一律用只读 `List` + 生成新实例。

</Callout>

## 练习

<Quiz
  index={1}
  question={
    <>
      <code>val readOnly: List&lt;String&gt; = mutableList</code> 之后，
      往 <code>mutableList</code> 里 add，<code>readOnly</code> 会变吗？
    </>
  }
  options={[
    '不会，List 是不可变的',
    '会，List 只是只读视图，不是不可变集合',
    '编译错误',
    '取决于 Kotlin 版本',
  ]}
  answer={1}
>

**会变**。`List` 是一个**只读视图接口**，它保证的是「通过这个引用你改不了」，
而不是「这份数据不会变」。

底层还是同一个 `ArrayList` 对象，别人持有可变引用就能改。甚至可以强转回
`MutableList` 直接改。

真正需要不可变时：

- `mutable.toList()` —— 复制一份独立的
- `kotlinx.collections.immutable` 的 `persistentListOf` —— 真正的持久化数据结构

Compose 里这个区别很关键：可变集合会让 Compose 无法正确判断重组时机。

</Quiz>

<Quiz
  index={2}
  question={
    <>
      为什么 <code>List&lt;out E&gt;</code> 是协变的，而 <code>MutableList&lt;E&gt;</code> 不是？
    </>
  }
  options={[
    '设计疏漏',
    '因为 MutableList 可以写入，协变会破坏类型安全（能往 MutableList<String> 里塞 Int）',
    '因为 MutableList 更慢',
    '因为 MutableList 是类不是接口',
  ]}
  answer={1}
>

协变的前提是**只读**。如果 `MutableList<String>` 能当 `MutableList<Any>` 用：

```
val strings: MutableList<String> = mutableListOf("a")
val anys: MutableList<Any> = strings      // 假设允许
anys.add(42)                               // 往 List<String> 里塞了 Int！
```

这正是 Java 数组协变导致 `ArrayStoreException` 的翻版。

`List<out E>` 因为只有读操作，协变是安全的——读出来的 `String` 一定也是 `Any`。

需要「只读地接受一个可变集合」时，用类型投影 `MutableList<out Any>`。

</Quiz>

<Quiz
  index={3}
  question={
    <>
      <code>buildList {'{'} ... {'}'}</code> 相比先 <code>mutableListOf()</code> 最后 <code>toList()</code> 好在哪？
    </>
  }
  options={[
    '性能更好',
    'lambda 内部可变、返回值只读，一步到位，且不会把可变引用泄漏出去',
    '支持并发',
    '没有区别',
  ]}
  answer={1}
>

`buildList` 的签名是 `buildList(builderAction: MutableList<T>.() -> Unit): List<T>`——
**内部给你可变能力，外部只暴露只读结果**。

好处：

- 不需要「先声明 mutable、最后转换」的两步
- 那个可变引用的作用域被限制在 lambda 内，不可能泄漏
- 需要条件性添加时很自然：`if (condition) add(x)`

同族的还有 `buildSet`、`buildMap`、`buildString`。

</Quiz>

<Quiz
  index={4}
  question="ViewModel 里数据更新了但 UI 不刷新，和集合有什么关系？"
  options={[
    '没关系',
    '如果原地修改 MutableList 后赋给 StateFlow，引用没变、equals 相等，StateFlow 会认为没变化而不发射',
    'StateFlow 不支持 List',
    '需要手动调用 notifyDataSetChanged',
  ]}
  answer={1}
>

`StateFlow` 会做**去重**（conflation）：新值和旧值 `equals` 时不发射。

原地修改可变集合再赋值，前后是**同一个对象**，`equals` 必然为 true，
于是这次更新被静默丢弃：

```
// ❌ UI 不刷新
_state.value = list.apply { add(newItem) }

// ✅ 生成新的不可变 List
_items.update { current -> current + newItem }
```

这是 Android 上「数据明明改了但界面没反应」最常见的原因之一。

规则：**放进 StateFlow 的集合状态一律用只读 `List`，每次更新生成新实例。**

</Quiz>
