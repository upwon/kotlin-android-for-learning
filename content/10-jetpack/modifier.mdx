`Modifier.padding(8.dp).clickable { }.background(Color.Red)` 这条链，
是 Kotlin **扩展函数** + **不可变链式构建**的教科书级应用。
理解它，顺便就理解了「为什么顺序会影响结果」这个高频困惑。

## 1. Modifier 是什么

```kt
// 简化后的本质
interface Modifier {
    fun then(other: Modifier): Modifier

    companion object : Modifier    // ← Modifier.padding 里的那个 Modifier
}
```

两个关键点：

- **`Modifier` 伴生对象**本身实现了 `Modifier`，代表「空修饰符」——
  这就是为什么可以写 `Modifier.padding(...)` 而不是 `EmptyModifier.padding(...)`
- 每个修饰符方法是**扩展函数**，返回**新的** `Modifier`，不修改原对象

```kt
// padding 的签名（简化）
fun Modifier.padding(all: Dp): Modifier = this.then(PaddingElement(all))
```

<Callout type="tip" title="这是 4.12 companion object 的一个巧妙用法">

`companion object : Modifier` 让**类名本身**成为一个可用的实例。

对比常见写法 `Modifier.Companion.empty()` 或者 `EmptyModifier`——
前者啰嗦，后者引入了一个新名字。让伴生对象直接实现接口，
调用点就变成了最简的 `Modifier.xxx()`。

见 [4.12 对象表达式与对象声明](/docs/04-classes/object-declarations)。

</Callout>

## 2. 为什么顺序重要

这是 Compose 里最高频的困惑：

```kt
// A：先 padding 再 background —— 背景不包含 padding 区域
Box(Modifier.padding(16.dp).background(Color.Red))

// B：先 background 再 padding —— 背景包含 padding 区域
Box(Modifier.background(Color.Red).padding(16.dp))
```

<Callout type="success" title="用 Kotlin 的角度理解">

`Modifier` 链是一个**有序的不可变列表**，从左到右依次应用：

```
Modifier.padding(16.dp).background(Color.Red)
   ↓ 展开
EmptyModifier.then(Padding(16)).then(Background(Red))
   ↓ 即
[Padding(16), Background(Red)]
```

布局时**从左往右**处理：先缩进 16dp，剩下的区域再画背景。
反过来则先在完整区域画背景，再缩进内容。

所以「顺序影响结果」不是什么魔法——它就是列表顺序。

</Callout>

同样的道理适用于 `clickable`：

```kt
// 点击区域不含 padding
Modifier.padding(16.dp).clickable { }

// 点击区域含 padding（点击热区更大，通常是你想要的）
Modifier.clickable { }.padding(16.dp)
```

<Callout type="tip">

记忆方式：**越靠左的修饰符，作用范围越「外」**。

想让点击热区大一点，`clickable` 就往左放；想让背景只覆盖内容，
`background` 就往右放。

</Callout>

## 3. 不可变链式构建

```kotlin
// 用纯 Kotlin 复现 Modifier 的机制
interface Mod {
    fun then(other: Mod): Mod = CombinedMod(this, other)
    companion object : Mod {
        override fun toString() = "Empty"
    }
}

class CombinedMod(private val outer: Mod, private val inner: Mod) : Mod {
    override fun toString() =
        if (outer === Mod) "$inner" else "$outer → $inner"
}

data class Padding(val dp: Int) : Mod {
    override fun toString() = "padding($dp)"
}

data class Background(val color: String) : Mod {
    override fun toString() = "background($color)"
}

// 扩展函数，返回新的 Mod，不修改原对象
fun Mod.padding(dp: Int): Mod = then(Padding(dp))
fun Mod.background(color: String): Mod = then(Background(color))

fun main() {
    val a = Mod.padding(16).background("Red")
    val b = Mod.background("Red").padding(16)

    println("A: $a")
    println("B: $b")

    // 不可变：base 没有被修改
    val base = Mod.padding(8)
    val ext1 = base.background("Blue")
    val ext2 = base.background("Green")
    println("base: $base")
    println("ext1: $ext1")
    println("ext2: $ext2")
}
```

跑一下能看到：`base` 被复用了两次，各自派生出不同的链，**原对象不受影响**——
这就是不可变构建器的价值。

## 4. 复用与提取

因为 `Modifier` 是不可变值，可以像普通值一样存起来复用：

```kt
// 提取成常量（在 Composable 外，避免每次重组重新构建）
private val CardModifier = Modifier
    .fillMaxWidth()
    .padding(horizontal = 16.dp, vertical = 8.dp)

@Composable
fun MyList(items: List<Item>) {
    LazyColumn {
        items(items) { item ->
            Card(modifier = CardModifier) { /* ... */ }
        }
    }
}
```

<Callout type="warn" title="别在 Composable 内部重复构建同一条链">

```kt
// 😐 每次重组都重新构建
@Composable
fun MyCard() {
    Card(Modifier.fillMaxWidth().padding(16.dp)) { }
}

// ✅ 提到外面，或者用 remember
private val CardModifier = Modifier.fillMaxWidth().padding(16.dp)
```

不过要注意：**只有不依赖任何参数的链才能提到顶层**。
依赖参数的用 `remember(key) { Modifier... }`。

这也是一个真实但容易被过度优化的点——简单的链构建开销很小，
先看 Layout Inspector 的数据再决定要不要优化。

</Callout>

## 5. 自定义 Modifier 扩展

```kt
// 自己写扩展函数，和官方的用法完全一致
fun Modifier.debugBorder(enabled: Boolean = BuildConfig.DEBUG): Modifier =
    if (enabled) this.border(1.dp, Color.Magenta) else this

// 条件式修饰符
inline fun Modifier.thenIf(condition: Boolean, block: Modifier.() -> Modifier): Modifier =
    if (condition) block() else this

// 用起来
Box(
    Modifier
        .fillMaxWidth()
        .thenIf(isSelected) { border(2.dp, Color.Blue) }
        .debugBorder()
)
```

<Callout type="tip">

`thenIf` 用的是 [5.2](/docs/05-functional/lambdas) 的**带接收者的 lambda**
`Modifier.() -> Modifier`——所以 `block` 里可以直接写 `border(...)`
而不是 `it.border(...)`。

这个小工具在真实项目里非常好用，值得放进公共代码。

</Callout>

## 6. 作用域限定的 Modifier

```kt
Column {
    Text("A", Modifier.weight(1f))        // ✅ weight 是 ColumnScope 的扩展
    Text("B", Modifier.align(Alignment.CenterHorizontally))
}

Box {
    Text("A", Modifier.align(Alignment.Center))   // ✅ BoxScope 的 align
    // Text("B", Modifier.weight(1f))             // ❌ BoxScope 没有 weight
}
```

`weight`、`align`、`matchParentSize` 这些**不是** `Modifier` 的通用扩展，
而是定义在 `ColumnScope` / `RowScope` / `BoxScope` 里的：

```kt
@LayoutScopeMarker
interface ColumnScope {
    fun Modifier.weight(weight: Float, fill: Boolean = true): Modifier
    fun Modifier.align(alignment: Alignment.Horizontal): Modifier
}
```

<Callout type="success">

注意 `fun Modifier.weight(...)` 是**定义在接口内部的扩展函数**——
这正是 [4.6 扩展](/docs/04-classes/extensions)和
[6.3 this 表达式](/docs/06-null-safety/this-expressions)里讲的**双接收者**：

- **扩展接收者** = `Modifier`
- **分发接收者** = `ColumnScope`

结果就是：只有在 `Column { }` 的作用域内，`Modifier` 上才「长出」`weight` 方法。
用错地方**编译期就报错**，不需要等到运行时发现布局不对。

`@LayoutScopeMarker` 就是 [9.4](/docs/09-advanced/type-safe-builders)
讲的 `@DslMarker`，防止嵌套时内层能调到外层的作用域方法。

</Callout>

## 7. Modifier 参数的约定

```kt
@Composable
fun MyComponent(
    text: String,
    modifier: Modifier = Modifier,      // ← 约定
    enabled: Boolean = true,
) {
    Column(modifier) {                   // ← 应用到最外层
        Text(text)
    }
}
```

三条官方约定：

1. **每个公开的 Composable 都应该接受 `modifier` 参数**——否则调用方无法调整布局
2. **它是第一个可选参数**，默认值 `Modifier`
3. **应用到最外层的元素**，而不是内部某个子元素

<Callout type="warn">

违反第 3 条会导致很诡异的行为：调用方写
`MyComponent(modifier = Modifier.padding(16.dp))`，
结果 padding 加在了内部的 Text 上而不是整个组件外面。

</Callout>

`Modifier` 链本质上是一个**有序的不可变列表**：

```
Modifier.padding(16).background(Red)
→ [Padding(16), Background(Red)]
```

从左往右应用：先缩进 16dp，在剩下的区域画背景。

就把 `clickable` 放在 `padding` 左边。

</Quiz>

<Quiz
  index={2}
  question={
    <>
      为什么可以直接写 <code>Modifier.padding(...)</code>，Modifier 不是接口吗？
    </>
  }
  options={[
    'Modifier 其实是一个类',
    '因为 Modifier 的 companion object 自己实现了 Modifier 接口，代表「空修饰符」',
    'padding 是静态方法',
    '这是编译器特殊处理',
  ]}
  answer={1}
>

```
interface Modifier {
    companion object : Modifier      // ← 伴生对象实现了自己的接口
}
```

伴生对象直接实现接口，于是**类名本身**就是一个可用的实例，
代表「空修饰符」。所有 `padding`、`background` 都是 `Modifier` 的扩展函数，
在这个空实例上开始链式调用。

对比其他设计：`EmptyModifier.padding()` 要多一个名字，
`Modifier.empty().padding()` 要多一次调用。这个做法让调用点最简洁。

见 [4.12 对象声明](/docs/04-classes/object-declarations)。

</Quiz>

<Quiz
  index={3}
  question={
    <>
      为什么 <code>Modifier.weight(1f)</code> 只能在 <code>Column</code>/<code>Row</code> 里用？
    </>
  }
  options={[
    '运行时检查',
    'weight 是定义在 ColumnScope/RowScope 内部的 Modifier 扩展函数（双接收者），只在该作用域内可见',
    'Box 不支持 weight',
    '这是文档约定，实际都能用',
  ]}
  answer={1}
>

```
interface ColumnScope {
    fun Modifier.weight(weight: Float, fill: Boolean = true): Modifier
}
```

这是**定义在接口内部的扩展函数**，同时有两个接收者：

- **扩展接收者** = `Modifier`
- **分发接收者** = `ColumnScope`

所以只有在 `Column { }` 提供的 `ColumnScope` 作用域里，`Modifier` 上才「长出」
`weight` 方法。在 `Box { }` 里用会**编译报错**——错误在编译期就被拦住了，
而不是运行时布局出问题。

这是 [4.6 扩展](/docs/04-classes/extensions) 双接收者能力最漂亮的应用之一。

</Quiz>

<Quiz
  index={4}
  type="multi"
  question="关于自定义 Composable 的 modifier 参数，哪些约定是对的？"
  options={[
    '每个公开的 Composable 都应该接受 modifier 参数',
    'modifier 应该是第一个可选参数，默认值为 Modifier',
    'modifier 应该应用到最外层元素',
    'modifier 应该应用到内部最主要的元素',
  ]}
  answer={[0, 1, 2]}
>

A、B、C 是官方 API 准则：

- **A**：不接受 `modifier` 的组件无法被调用方调整布局，复用性大打折扣
- **B**：`modifier` 是最常被覆盖的参数，放第一个可选位置可以按位置传，
  不用每次写 `modifier = `
- **C**：应用到最外层，语义才符合直觉

**D 是错的**，而且是常见 bug：调用方写
`MyComponent(modifier = Modifier.padding(16.dp))` 期望整个组件外面有间距，
结果 padding 加在了内部某个 Text 上——表现出来就是「这个 modifier 好像没用」。

</Quiz>
