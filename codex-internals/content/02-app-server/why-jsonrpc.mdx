`codex app-server` 的第一句自我介绍是这样的：

> Similar to [MCP](https://modelcontextprotocol.io/), `codex app-server` supports bidirectional
> communication using JSON-RPC 2.0 messages (with the `"jsonrpc":"2.0"` header omitted on the wire).

**"Similar to MCP"** —— 借了形，没借神。这一章讲为什么。

## MCP 给不了的三件事

### 1. 服务端向客户端发起请求

审批是 agent 的核心交互：模型要跑 `rm -rf build/`，得先问人。这件事的形状是
**服务端发起、等一个答复**——它是个请求，不是通知。

app-server 的 `ServerRequest` 有 9 种：

| 方法 | 干什么 |
| --- | --- |
| `item/commandExecution/requestApproval` | 命令执行审批 |
| `item/fileChange/requestApproval` | 文件改动审批 |
| `item/permissions/requestApproval` | 权限请求审批 |
| `item/tool/requestUserInput` | 模型中途向人要信息 |
| `mcpServer/elicitation/request` | 把下游 MCP 服务器的 elicitation 透传给最终用户 |
| `item/tool/call` | 动态工具调用（实验性） |
| `account/chatgptAuthTokens/refresh` | 让客户端刷新令牌 |
| `attestation/generate` | 让客户端产生证明 |
| `currentTime/read` | 读客户端的当前时间 |

<Callout type="note" title="最后三个才是真正说明问题的">

前面几个还能勉强用「服务端通知 + 客户端再发一个请求」凑出来。
但 `currentTime/read`、`attestation/generate`、`chatgptAuthTokens/refresh` 不行——
它们的语义就是「我需要你算个东西给我，我等着」。

服务端**依赖客户端的能力**，这在「客户端问、服务端答」的模型里是表达不出来的。

</Callout>

### 2. 有状态的、长期存在的资源

MCP 的资源模型是无状态的读取。而 thread 是：

- 有 id、能落盘、进程重启后还在；
- 能 `resume`、能 `fork`（还能指定从哪个 turn 切）、能 `archive` / `unarchive` / `delete`；
- 能被分组（section）、能被搜索、能分页列出；
- 有生命周期状态（`ThreadStatus`），前端要能订阅它的变化。

这已经不是"资源"，是一个**有生命周期的领域对象**。

### 3. 事件密度

一次 turn 会推出几十到上百条通知：item 的增删改、逐字 delta、命令输出流、
推理摘要、token 用量、diff 更新、计划更新……协议里定义了 **71 种通知**。

这个量级需要**按连接、按 thread 精细控制订阅**，还需要能退订
（`optOutNotificationMethods`，见 2.3）。

## 那为什么还要"像 MCP"

因为 MCP 已经解决的部分不值得重新发明：

- **JSON-RPC over stdio** 是个已经被验证过的、生态齐全的传输形态；
- IDE 扩展作者已经熟悉这个形状；
- 请求 / 响应 / 通知的三分法本身没问题。

Codex 保留了这些，换掉了语义层。这是个很务实的选择——**在别人解决好的地方复用，
在别人解决不了的地方另起炉灶**。

## 省掉 `"jsonrpc":"2.0"` 这一行

<Callout type="design" title="值不值">

**收益**：一次 turn 上百条消息，每条省 18 字节。对 stdio 上的高频事件流，这不是零。

**代价**：不再是严格合规的 JSON-RPC 2.0，通用的 JSON-RPC 库不能直接用，
客户端得按 Codex 的形状来。

考虑到这个协议的客户端本来就只有"实现了 Codex 集成的人"，这个交换是划算的。
但它确实说明了一件事：**这不是一条给通用工具消费的协议**，它是给 Codex 前端用的。

</Callout>

## 协议的规模

| 类别 | 数量 | 定义在 |
| --- | --- | --- |
| 客户端请求 `ClientRequest` | 137 种 | `protocol/common.rs` |
| 服务端通知 `ServerNotification` | 71 种 | 同上 |
| 服务端请求 `ServerRequest` | 9 种 | 同上 |

三个巨大的枚举，全部由**同一个宏**从声明式列表生成（2.5 会展开）。
每一项写起来是这样：

```rust
ThreadResume => "thread/resume" {
    params: v2::ThreadResumeParams,
    inspect_params: true,
    serialization: thread_or_path(params.thread_id, params.path),
    response: v2::ThreadResumeResponse,
},
```

一行声明同时决定了：线上的方法名、参数类型、响应类型、**并发时怎么排队**、
以及要不要检查实验性字段。这是这个协议最值得学的一处工程手法。

审批、elicitation 透传、以及 `currentTime/read` 这类「服务端依赖客户端能力」的调用，
本质都是**反向请求**。MCP 的形状里没有这个位置。

至于 A：省掉 `jsonrpc` 字段确实是为了体积，但那是优化，不是动机。
C 错：MCP 本来就用 stdio。D 不准确：Codex 把协议、schema 生成、SDK 全开源了，
还提供 `generate-ts` 让第三方拿到精确类型——恰恰是在降低集成门槛。

</Quiz>

## 一句话结论

agent 前端要的是「双向、有状态、事件密集」，这正好是 MCP 的三个弱项。
