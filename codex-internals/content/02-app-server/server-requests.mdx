**方向反过来的那一半协议。** 这是 app-server 不能直接用 MCP 的根本原因（2.1），
也是整条链路上最容易做错的地方。

## 九种反向请求

| 方法 | 谁触发 | 客户端要做什么 |
| --- | --- | --- |
| `item/commandExecution/requestApproval` | 模型要跑命令 | 展示命令 + cwd，让用户选 |
| `item/fileChange/requestApproval` | 模型要改文件 | 展示 diff，让用户选 |
| `item/permissions/requestApproval` | 需要额外权限 | 展示请求的权限 |
| `item/tool/requestUserInput` | 模型中途要信息 | 弹输入框 |
| `mcpServer/elicitation/request` | 下游 MCP 服务器要信息 | 按 mode 渲染表单 / URL |
| `item/tool/call`（实验性） | 动态工具 | 由客户端执行工具 |
| `account/chatgptAuthTokens/refresh` | 令牌过期 | 刷新并回传 |
| `attestation/generate` | 上游需要证明 | 生成并回传 token |
| `currentTime/read` | 时间提醒到期 | 回一个 Unix 时间戳 |

## 决定不只是"同意 / 拒绝"

命令审批支持六种决定：

| decision | 含义 |
| --- | --- |
| `accept` | 这一次同意 |
| `acceptForSession` | 本会话内同类命令都同意 |
| `decline` | 拒绝 |
| `cancel` | 取消（连带停掉这一步） |
| `acceptWithExecpolicyAmendment` | 同意，**并把规则写进 execpolicy** |
| `applyNetworkPolicyAmendment` | 同意，**并加一条网络策略** |

后两种很有意思——它们带着结构化的载荷：

```json
{
  "decision": {
    "applyNetworkPolicyAmendment": {
      "network_policy_amendment": { "host": "example.com", "action": "allow" }
    }
  }
}
```

<Callout type="design" title="把「以后别再问我」做成策略修订，而不是一个记忆开关">

最省事的做法是记一个「用户批准过 `curl example.com`」的哈希。
Codex 走的是另一条：用户的这次批准会变成一条**可检查、可审计、可撤销的策略规则**，
写进 execpolicy 或网络策略里（5.5、5.6）。

代价是复杂度高得多；收益是安全边界始终是显式的，而不是散落在一堆历史批准里。

服务端还会通过 `proposedExecpolicyAmendment` / `proposedNetworkPolicyAmendments`
**预先给出建议的规则**，客户端直接展示即可，不用自己组装。

</Callout>

## `availableDecisions`：让服务端决定按钮

请求里可能带 `availableDecisions`。README 的建议是：

> Clients can prefer `availableDecisions` when present to render the exact set of choices the
> server wants to expose, while still falling back to the older heuristics if it is omitted.

这样服务端可以在不同场景下收窄选项（比如纯网络审批时不显示 execpolicy 相关的按钮），
**而不需要每个客户端各自实现一套判断逻辑**。这是个很好的向后兼容做法：
新字段优先，缺了就退回旧启发式。

## 客户端不回答会怎样

分情况，而且**没有统一的"超时就当同意"**：

- `item/tool/requestUserInput` 带一个必填的 `isBlocking`，告诉客户端要不要无限等待
  （旧的 `autoResolutionMs` 已废弃，只为兼容保留）；
- `currentTime/read` **失败、取消、超时或格式错误，都会在发模型请求之前停掉这个 turn**；
- `attestation/generate` 在 app-server 自己这一侧失败时，会用状态码代替 token 往上游发
  （`1 = timeout`、`2 = request failed`、`3 = request canceled`、`4 = malformed response`）；
  没有客户端 opt-in 时，直接不带这个头。

<Callout type="warn" title="能力要在 initialize 里声明">

`attestation/generate` 只发给在 `initialize` 时设了
`capabilities.requestAttestation` 的客户端。没声明就不会收到——
反过来，声明了却不实现，会让 turn 卡住。

</Callout>

## MCP elicitation 的三种模式

下游 MCP 服务器要问用户话时，`mcpServer/elicitation/request` 会带三种 mode 之一：

```json
{ "mode": "form",        "message": "…", "requestedSchema": { } }
{ "mode": "openai/form", "message": "…", "requestedSchema": { } }
{ "mode": "url",         "message": "…", "url": "…", "elicitationId": "…" }
```

客户端回 `{ "action": "accept" | "decline" | "cancel", "content": … }`。

<Callout type="note" title="这条链有三跳">

MCP 服务器 → Codex（当 MCP client）→ app-server → 前端 → 用户。

中间每一跳都要能**转发一个需要答复的请求**。如果 app-server 这一层只有通知没有反向请求，
这条链在这里就断了——这就是 2.1 里说的"MCP 表达不了"的具体后果。

</Callout>

## 一句话结论

审批不是「弹个框」，它是协议里一等的反向 RPC；链路上每一层都要能转发它，
每一个 pending 请求都要能被清理。
