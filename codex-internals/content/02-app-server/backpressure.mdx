一个能同时跑几十个 thread、每个 thread 每秒推几十条事件的服务，**必须能说"我忙不过来"**。
这一章讲它怎么说。

## 三段有界队列

> The server uses bounded queues between transport ingress, request processing, and outbound writes.

```text
transport 入站  ──▶  请求处理  ──▶  出站写入
     │                  │              │
   有界              有界           有界
```

全都是**有界**的。这是刻意的：无界队列在过载时不会报错，只会悄悄吃内存，
直到某个更糟的时刻崩掉。

## 过载时返回 -32001

> When request ingress is saturated, new requests are rejected with a JSON-RPC error code
> `-32001` and message `"Server overloaded; retry later."`.
>
> Clients should treat this as retryable and use exponential backoff with jitter.

`-32001` 在 JSON-RPC 的实现自定义区间里。客户端看到它应该：

- 认为这是**可重试**的，不是永久失败；
- 用**带抖动的指数退避**，不要定时重试（不然一堆客户端会同步撞上来）。

<Callout type="tip" title="给客户端作者">

不要把 `-32001` 和别的错误一起归到"请求失败，提示用户"。它是背压信号，
正确的反应是等一会儿再试——把它当成致命错误会让用户在服务端稍微卡一下的时候看到一堆报错。

</Callout>

## 一条关键的不变量

`in_process.rs` 的模块注释把它写得最清楚：

> Command submission uses `try_send` and can return `WouldBlock`, while event fanout may drop
> notifications under saturation. **Server requests are never silently abandoned**: if they cannot
> be queued they are failed back into `MessageProcessor` with overload or internal errors so
> approval flows do not hang indefinitely.

拆开看：

| 消息种类 | 过载时 |
| --- | --- |
| 客户端提交的命令 | `try_send` 返回 `WouldBlock`，调用方知道没送进去 |
| 事件通知 | **可以丢**（in-process 里表现为 `Lagged`） |
| 服务端发起的请求 | **绝不静默丢弃**，送不进去就以过载/内部错误失败回去 |

<Callout type="success" title="为什么这条不变量这么重要">

设想它不成立：模型要跑一条命令，服务端向客户端发审批请求，队列满了，请求被丢掉。

结果是——**内核在等一个永远不会到来的答复**。那个 turn 就永久挂住了，
用户看到的是"卡死"，日志里什么都没有。

把审批做成必须有答复的请求（2.8），就必须配套保证"送不出去也要有个失败答复"。
这两件事是一体的。

</Callout>

## 事件为什么可以丢

因为事件的语义是**呈现**，不是状态转移。丢掉几个 delta，最坏是中间少显示几个字；
而 `item/completed` 这类权威事件承载着最终状态——只要它到了，UI 就能收敛到正确状态。

这也解释了 2.7 里那条建议：**以 `item/completed` 为准，不要靠 delta 累加**。
它不只是"更准确"，在背压下它是**唯一正确**的做法。

<Callout type="warn" title="Lagged 不是可以忽略的">

`InProcessServerEvent::Lagged` 明确告诉调用方"你漏掉了一些事件"。
正确的反应通常是**重新拉一次状态**（比如 `thread/read`），而不是当没发生过。

</Callout>

## 排队深度是可观测的

`request_serialization.rs` 里注册了 gauge：

```rust
static QUEUED_REQUESTS: Gauge = Gauge::new("app.requests.queued");
```

配合 `server/diagnostics`（实验性）能读到进程本地的内存测量与已注册的诊断 gauge。
排查"客户端说服务端卡了"这类问题时，先看这个数。

## 一张总结表

| 层 | 满了怎么办 | 谁负责恢复 |
| --- | --- | --- |
| 入站请求 | 拒绝，`-32001` | 客户端退避重试 |
| 事件出站 | 丢弃 / `Lagged` | 客户端重新拉状态 |
| 服务端请求出站 | 失败回内核 | 内核把那一步标成失败，turn 继续或结束 |

  type="single"

    '重新拉一次状态（比如 thread/read），让 UI 收敛到服务端的真实状态',
    '立刻断开重连',
    '把这个 turn 标成失败',
  ]}
  answer={1}
>

`Lagged` 的含义是"你漏了一些事件"。继续增量更新会让 UI 停留在一个不完整的状态上，
而且**永远不会自己修好**。

重连（C）过重；标失败（D）不对——turn 本身可能跑得好好的，只是通知没送到。
重新拉一次权威状态是最小且正确的动作。

</Quiz>

## 一句话结论

「事件允许丢、请求必须回」这条不变量，是整个审批链不会挂死的原因。
