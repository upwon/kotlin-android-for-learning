同一套 JSON-RPC 语义，四种字节进出的方式。

## 四种

| `--listen` | 形态 | 谁在用 |
| --- | --- | --- |
| `stdio://`（默认，或 `--stdio`） | 换行分隔的 JSON（JSONL） | IDE 扩展、绝大多数客户端 |
| `ws://IP:PORT` | 每个 websocket 文本帧一条消息 | **实验性 / 不支持** |
| `unix://[PATH]` | unix socket 上跑 websocket（HTTP Upgrade 握手） | 本地控制面、daemon |
| `off` | 不开任何本地监听 | 只做进程内嵌入（TUI / exec） |

## stdio：默认那条

JSONL：一行一条 JSON 消息。它是默认的原因很实际——

- 子进程模型天然带**生命周期绑定**：父进程死了，管道断了，服务端自然退出；
- 不需要端口、不需要鉴权、不会被别的进程连上；
- 每个客户端一个进程，隔离性最好。

## websocket：带健康探针，但别用

```text
GET /readyz   → 200，一旦监听器开始接受新连接
GET /healthz  → 200，且请求不带 Origin 头
任何带 Origin 头的请求 → 403 Forbidden
```

<Callout type="warn" title="Origin 一律 403 不是 bug">

带 `Origin` 头意味着请求来自浏览器页面。一个能启动任意命令的本地服务，
**绝对不能被网页连上**——那是标准的 DNS rebinding 攻击面。

直接拒绝所有带 Origin 的请求，是最省事也最不会出错的做法。

README 里明确写了 websocket transport 是 experimental / unsupported，
不要用在生产上。

</Callout>

## unix socket：本地控制面

默认路径 `$CODEX_HOME/app-server-control/app-server-control.sock`，
上面跑的仍然是 websocket（走标准 HTTP Upgrade 握手）。

配套有两个中继工具：

```bash
# 打开一条到控制 socket 的原始流，在它和 stdin/stdout 之间转发字节
codex app-server proxy [--sock PATH]

# 同样的事情，作为隐藏子命令存在
codex stdio-to-uds
```

有了它们，**只会说 stdio 的客户端也能连上一个已经在跑的 app-server**。
这是 daemon 与 remote control 的基础（2.13）。

## off：第四种，其实没有 transport

`--listen off` 时不开任何本地监听。这对应的是 `in_process` 模式：
transport 被换成**内存 channel**，协议语义一个不少。

用它的正是 TUI 和 `codex exec`。2.10 整章讲这个。

## 日志与观测

```bash
RUST_LOG=codex_app_server=debug   # 过滤与级别
LOG_FORMAT=json                   # tracing 日志以 JSON 输出到 stderr，一行一条
```

注意是 **stderr**——stdio transport 占着 stdout，日志不能往那儿写。

## code-mode host 是另一回事

```bash
codex app-server --code-mode-host wss://HOST/PATH
```

这个 `wss://` 和 `--listen` 无关：它是 app-server **主动向外**连的一条连接，
用来接远程 code-mode 宿主，进程内的多个 thread 共享它（4.7）。

`Origin` 是浏览器自动加的。一个本地的、能起进程改文件的服务，一旦能被网页连上，
就等于把任意代码执行暴露给了任何一个你访问过的站点（DNS rebinding）。

一刀切拒绝比逐条判断白名单更不容易出错——这类地方**保守是对的**。

</Quiz>

## 一句话结论

transport 只换「字节怎么进出」，上面的 JSON-RPC 语义一模一样。
