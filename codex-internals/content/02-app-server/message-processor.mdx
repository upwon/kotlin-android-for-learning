所有请求都从这里分岔。这一章看三件事：**怎么进来、怎么排队、怎么分发**。

## 两个入口，一个出口

```rust
// JSON 那条：stdio / websocket / unix socket 都走这里
pub(crate) async fn process_request(&self, /* … */ request: JSONRPCRequest, /* … */)

// 类型化那条：in-process 嵌入者走这里，跳过 JSON 反序列化
pub(crate) async fn process_client_request(&self, /* … */ request: ClientRequest, /* … */)
```

`process_client_request` 的文档注释把设计意图写得很明白：

> Handles a typed request path used by in-process embedders.
>
> This bypasses JSON request deserialization but keeps identical request semantics by delegating
> to `handle_client_request`.

<Callout type="success" title="这就是 2.10 那条线的根">

两个入口，**同一个 `handle_client_request`**。in-process 省掉的只有
「JSON 字符串 ↔ Rust 类型」这一步，其余每一行代码都共享。

所以 TUI 遇到的行为和 IDE 扩展遇到的行为，在语义上必然一致——
不是靠约定，是靠只有一份实现。

</Callout>

## 请求的三种并发命运

这是 `message_processor.rs` 里最值得学的一段。每个请求进来后：

```rust
let serialization_scope = codex_request.serialization_scope();
// …把真正的处理逻辑包成 QueuedInitializedRequest（带 rpc_gate）…

if let Some(scope) = serialization_scope {
    let (key, access) = RequestSerializationQueueKey::from_scope(connection_id, scope);
    self.request_serialization_queues.enqueue(key, access, request).await;
} else {
    tokio::spawn(async move { request.run().await; });
}
```

<Source path="codex-rs/app-server/src/message_processor.rs" lines="843-882" />

于是有三种命运：

| `serialization` | 行为 |
| --- | --- |
| `None` | 直接 `tokio::spawn`，完全并发 |
| 某个 scope + `Exclusive` | 进该 key 的队列，**串行** |
| 某个 scope + `SharedRead` | 进队列，但**可以和其它 SharedRead 并行** |

### 排队的 key 是什么

`RequestSerializationQueueKey` 的取值就是答案：

```rust
Global(&'static str)                 // 全局互斥，比如配置写入
Thread { thread_id }                 // 按 thread 串行
ThreadPath { path }                  // 按 thread 文件路径串行
CommandExecProcess { connection_id, process_id }
Process { connection_id, process_handle }
FuzzyFileSearchSession { session_id }
FsWatch { connection_id, watch_id }
McpOauth { server_name }
```

注意几个 key 里带了 `connection_id`——**同一个进程里不同连接的进程句柄不能互相干扰**，
而 `Thread` 和 `ThreadPath` 不带，因为一个 thread 全局只有一份。

### 声明在哪

不在 app-server 里，在**协议定义**里。回看 2.1 那段宏：

```rust
ThreadResume => "thread/resume" {
    params: v2::ThreadResumeParams,
    serialization: thread_or_path(params.thread_id, params.path),
    response: v2::ThreadResumeResponse,
},
ThreadArchive => "thread/archive" {
    params: v2::ThreadArchiveParams,
    serialization: thread_id(params.thread_id),
    response: v2::ThreadArchiveResponse,
},
```

<Callout type="design" title="把并发语义放进协议声明里">

「两个 `thread/archive` 打到同一个 thread 上会不会互相踩」——
这个问题的答案，写在**协议定义**旁边，不是埋在实现的某个 `Mutex` 里。

新增一个方法时，作者必须回答"它跟谁互斥"，因为宏要求填 `serialization` 这一项。
**用类型系统逼着人回答关键问题**，比写在贡献指南里管用得多。

</Callout>

## 连接级闸门

真正的处理逻辑被包在 `QueuedInitializedRequest` 里，跑之前要先过 `ConnectionRpcGate`：

> Closing the gate prevents queued handlers from starting while allowing handlers that already
> acquired a token to finish.

关闸之后，**已经拿到令牌的继续跑完，还在排队的直接不跑**。
这就是连接断开时的清理语义：不粗暴地 abort 正在进行的工作，但也不再开新的。

## 分发

过了闸门和队列，才到 `handle_initialized_client_request` —— 一个 137 分支的 `match`：

```rust
let result: Result<Option<ClientResponsePayload>, JSONRPCErrorError> = match codex_request {
    ClientRequest::Initialize { .. } => { /* … */ }
    ClientRequest::ServerDiagnostics { .. } => Ok(Some(read_server_diagnostics().into())),
    ClientRequest::ConfigRead { params, .. } => self.config_processor.read(params).await,
    ClientRequest::FsReadFile { params, .. } => self.fs_processor.read_file(params).await,
    ClientRequest::ThreadStart { params, .. } => { /* … */ }
    // …一百三十多个分支…
};
```

每个分支都很薄——**几乎都是一行转发给某个 processor**。重逻辑全在
`request_processors/` 下（2.6）。

`ThreadArchive` 在协议里声明了 `serialization: thread_id(params.thread_id)`，
于是它们被映射到同一个 `RequestSerializationQueueKey::Thread`，进同一条队列串行跑。

如果 thread_id 不同，key 不同，队列不同，两者并发——**这正是按 key 排队而不是全局锁的价值**。

</Quiz>

## 一句话结论

`ClientRequest` 是个 137 分支的巨大枚举，但每个分支都薄——重逻辑全在 processor 里，
并发语义全在协议声明里。
