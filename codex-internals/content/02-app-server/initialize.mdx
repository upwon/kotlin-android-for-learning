**每条连接一次**，两步，顺序不能反。

## 两步

```json
{
  "method": "initialize",
  "id": 0,
  "params": {
    "clientInfo": {
      "name": "codex_vscode",
      "title": "Codex VS Code Extension",
      "version": "0.1.0"
    }
  }
}
```

服务端回一个响应（里面有它将向上游出示的 User-Agent、`codexHome` 路径、
`platformFamily` / `platformOs`），然后客户端发一条 `initialized` 通知。

握手之后才能发别的请求。规则很硬：

| 情况 | 结果 |
| --- | --- |
| 握手前发别的请求 | `"Not initialized"` 错误 |
| 同一连接上再发一次 `initialize` | `"Already initialized"` 错误 |

<Callout type="warn" title="「服务端不给我发事件」，八成是这里">

握手是**每条连接**的，不是每进程、每 thread。多开一条连接就要再走一次。
而且 `initialized` 那条通知不能省——只发 `initialize` 请求是不够的。

</Callout>

## clientInfo 不只是装饰

```text
clientInfo.name  →  合规日志平台用它识别客户端
                 →  上游 User-Agent
                 →  遥测维度
```

README 里有一句给企业集成者的提示：如果你在做面向企业的 Codex 集成，
需要联系 OpenAI 把你的 `name` 加进已知客户端列表，否则 Compliance Logs 那边认不出来。

## 能力协商

`initialize.params.capabilities` 里客户端声明自己能做什么。三类：

### 1. 实验性 API 开关

```json
{ "capabilities": { "experimentalApi": true } }
```

不开这个开关，实验性的方法与字段对你不可见（2.12）。

### 2. 通知退订

```json
{
  "capabilities": {
    "optOutNotificationMethods": ["thread/started", "item/agentMessage/delta"]
  }
}
```

**精确匹配，不支持通配符或前缀**。未知的方法名会被接受并忽略——
这样客户端可以照着新版本的方法名写，在老服务端上也不会报错。

71 种通知里，一个具体的前端通常只画得出其中一部分。退订掉画不出来的，
能显著减少 stdio 上的流量——尤其是 `item/agentMessage/delta` 这种逐字推送的。

### 3. MCP 扩展

```json
{
  "capabilities": {
    "extensions": {
      "openai/form": {},
      "io.modelcontextprotocol/ui": {
        "mimeTypes": ["text/html;profile=mcp-app"]
      }
    }
  }
}
```

<Callout type="design" title="为什么存的是整个值，而不是一个布尔">

app-server 把 `io.modelcontextprotocol/ui` 下面的**完整值**保留下来，
而不是从中推导出一个「支不支持 WebView」的布尔。

这样客户端可以声明更多的 MIME 类型和将来的扩展设置，而**服务端不用跟着改**。
把结构化的能力声明压成一个布尔，是很常见也很难回头的设计错误。

</Callout>

## 扩展 profile 在 thread 创建时被冻结

这是个容易踩的语义：

> The MCP extension profile is fixed when a Codex session is created by
> `thread/start`, `thread/resume`, or `thread/fork`.

也就是说：

- 这个 profile 会被写进 Codex 向下游 MCP 服务器发的 `initialize` 里；
- **这个 session 里之后所有的 turn 和 MCP 工具调用都用这份 profile**；
- 另一条 app-server 连接**不能**通过后来起一个 turn 来改它；
- 子 agent 的 session 继承同一份 profile。

<Callout type="tip" title="推论">

如果你的客户端要改扩展能力（比如新增支持一种 MIME），**必须重新起 thread**，
在已有 thread 上改是无效的。

</Callout>

## in-process 模式下呢

`codex-app-server-client` 这个门面会**自动完成握手**——它在 `start` 里就把
initialize / initialized 走完了，调用方拿到的是一个已就绪的 handle（2.10）。

## 一句话结论

很多「服务端不给我发事件」的问题，根因是 `initialized` 这一步没做。
