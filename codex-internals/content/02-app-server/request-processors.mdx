## 按家族分

### thread 家族

| 文件 | 行数 | 管什么 |
| --- | --- | --- |
| `thread_processor.rs` | ~5500 | 主体：读、列、更新、事件桥接 |
| `thread_lifecycle.rs` | ~875 | start / resume / fork 的生命周期 |
| `thread_goal_processor.rs` | ~468 | thread 的目标（goal）设置与延续 |
| `thread_summary.rs` | ~334 | 摘要 |
| `thread_sections.rs` | ~195 | 分组 |
| `thread_resume_redaction.rs` | ~232 | resume 时的敏感信息脱敏 |
| `thread_delete.rs` / `thread_enrichment.rs` / `thread_fork_goal.rs` | 小 | 各自一件事 |

`thread_processor.rs` 一个文件 5500 行，是这个目录里最大的。原因不难理解：
thread 是协议里唯一有完整生命周期的资源，它的 API 面本来就最宽。

### turn 家族

`turn_processor.rs`（~1513 行）管 `turn/start`、`turn/interrupt`、`turn/steer`、
review 请求，以及把内核事件桥接成协议通知。第 1.2 章那条主链的 ② 就在这里。

### 配置家族

- `config_processor.rs` —— `config/read`、`config/write`、批量写；
- `config_manager.rs` / `config_manager_service.rs`（在上一层目录）—— 配置的加载、
  分层与变更传播；
- `config_errors.rs` —— 配置解析失败时怎么报给客户端。

<Callout type="note" title="为什么配置要走协议">

一个很自然的疑问：IDE 扩展自己读 `config.toml` 不行吗？

不行。`config.toml` 有分层（全局 / 项目 / 命令行覆盖）、有校验、有 profile。
如果每个前端自己解析，很快就会出现"TUI 认为的配置"和"IDE 认为的配置"不一致。
把它做成协议方法，配置的解释权就只有一个地方。

同样的逻辑也解释了下面这一组。

</Callout>

### 宿主能力家族

这一组是最容易被问"为什么要有"的：

| 文件 | 提供什么 |
| --- | --- |
| `fs_processor.rs` | 读写文件、建目录、读元数据、列目录、删、拷 |
| `git_processor.rs` | git 相关查询 |
| `process_exec_processor.rs` | 带生命周期的进程执行（起、写 stdin、读输出、杀） |
| `command_exec_processor.rs` | 一次性命令执行 |
| `search.rs` | 模糊文件搜索 |

编辑器明明自己就能读文件，为什么还要通过 app-server？

**因为执行环境可能不在本地。** 当 thread 绑定到一个远程环境（`exec-server`，7.4）时，
"读文件"要读的是**那边**的文件。把宿主能力也放进协议，本地场景和远程场景就能走同一套代码。

### 账号与模型

- `account_processor.rs`（~1421 行）—— 登录、登出、账号信息、限额；
- `catalog_processor.rs` —— 模型目录；
- `models_refresh_worker.rs`（上一层）—— 后台刷新模型列表；
- `bedrock_auth.rs` —— AWS Bedrock 的认证路径。

### 扩展与其它

`plugins.rs`（~2487 行）、`mcp_processor.rs`、`apps_processor/`、
`marketplace_processor.rs`、`environment_processor.rs`、`windows_sandbox_processor.rs`、
`remote_control_processor/`、`feedback_processor.rs`、`diagnostics.rs`。

## 一个典型 processor 长什么样

拿最小的 `fs_processor.rs`（219 行）当样本，模式基本是：

```rust
// 1. 从 params 里拿到路径 / 参数
// 2. 解析到正确的执行环境（本地 or 远程）
// 3. 做事，把 io::Error 映射成 JSON-RPC 错误码
// 4. 返回类型化的 Response
```

**processor 里不做并发控制**——那一层在 `message_processor` 的排队机制里已经处理过了（2.5）。
这也是为什么这些文件能保持得这么薄。

## 找东西的顺序

<Callout type="success" title="三步定位法">

1. 在 `app-server/README.md` 的 API Overview 里找到方法名（比如 `thread/fork`）；
2. 在 `protocol/common.rs` 里搜这个方法名，拿到它的 `params` 类型和 `serialization`；
3. 在 `request_processors/` 里找同名文件（`thread_lifecycle.rs`），从那里往内核走。

三步之内必到。

</Callout>
