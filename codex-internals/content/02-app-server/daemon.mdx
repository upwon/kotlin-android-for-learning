前面十二章讲的 app-server，生命周期都绑在启动它的那个东西上：
IDE 扩展关了、终端关了，服务就没了。**daemon 把这条线剪断。**

## 它解决什么

一句话：**让 app-server 活得比某一个前端更久**。

具体场景：

- 桌面端和 IDE 想连同一个正在跑的 Codex，而不是各起一个；
- 关掉终端之后，正在跑的 turn 不该跟着死；
- 手机 / 另一台机器想接管这台机器上的会话（remote control）。

## 三个命令

```bash
codex remote-control start   # 启动 app-server daemon，并打开远程控制
codex remote-control stop    # 停掉 daemon
codex remote-control pair    # 生成一个短时效的手工配对码
```

## 控制面在哪

daemon 复用的正是 2.2 讲过的 **unix socket 控制面**：

```text
$CODEX_HOME/app-server-control/app-server-control.sock
```

上面跑 websocket（HTTP Upgrade 握手）。只会说 stdio 的客户端可以用
`codex app-server proxy` 或 `stdio-to-uds` 中继过去。

<Callout type="note" title="daemon 不是新内核">

值得反复强调：daemon **没有引入新的协议，也没有新的执行语义**。
它做的事是"启动一个 app-server 进程、管好它的生命周期、把控制面 socket 准备好"。

`lib.rs` 里那几个常量就很能说明它的定位——它主要在做进程编排：

- `START_POLL_INTERVAL = 50ms` —— 启动后轮询就绪
- `START_TIMEOUT = 10s` —— 启动超时
- `OPERATION_LOCK_TIMEOUT = 75s` —— 操作互斥锁的超时

</Callout>

## 模块构成

| 模块 | 干什么 |
| --- | --- |
| `backend/` | 后端类型（`BackendKind`）与路径解析 |
| `client.rs` | 连接到 daemon 的客户端 |
| `managed_install.rs` | 托管安装：daemon 可以管理一份自己用的 codex 二进制 |
| `update_loop.rs` | 后台更新循环 |
| `remote_control_client.rs` | 远程控制那一侧 |
| `settings.rs` | daemon 自己的设置 |

`managed_install` + `update_loop` 这一对说明 daemon 还兼了个角色：
**它可以自己保有并更新一份 codex 二进制**，而不是依赖用户 PATH 里那个。
对一个"应该一直在后台跑着"的东西来说，这是必要的。

## 远程控制的协议面

`ClientRequest` 里有一整族：

| 方法 | 用途 |
| --- | --- |
| `remoteControl/enable` | 打开远程控制 |
| `remoteControl/disable` | 关掉 |
| `remoteControl/status/read` | 读状态 |
| `remoteControl/pairing/start` | 开始配对 |
| `remoteControl/pairing/status` | 配对状态 |
| `remoteControl/clients/list` | 列出已配对的客户端 |
| `remoteControl/clients/revoke` | 吊销某个客户端 |

配套一条通知：`remoteControl/status/changed`。

<Callout type="design" title="配对 + 列表 + 吊销">

这三个凑在一起是个很明确的信号：远程控制被当成**设备授权**来做，而不是"开个端口加个密码"。

- 配对码是**短时效**的（`pair` 子命令的描述里写着 short-lived）；
- 已授权的客户端可以被列出来；
- 任何一个都可以被单独吊销。

对一个能在你机器上跑任意命令的服务来说，这是最低限度的要求。
对照 2.2 里 websocket 监听器对 `Origin` 一刀切 403——同一种保守。

</Callout>

## 和其它章的关系

- **2.2 transport** —— daemon 用的就是 unix socket 那一种；
- **2.10 in-process** —— `AppServerClient` 那个枚举里的 `Remote` 变体，

- **7.1 桌面端 / 7.3 remote control** —— 上层的使用场景在那两章。

daemon 是进程编排，不是新内核。协议、审批、沙箱全都原样保留——
D 那种"为了无人值守就绕过安全检查"的做法，恰恰是这个仓库处处在避免的。

C 描述的是 exec-server（7.4），那是另一件事：把**执行环境**搬远，而不是把内核搬远。

</Quiz>

## 一句话结论

daemon 不是新内核，它只是把同一个 app-server 的生命周期拉长了。
