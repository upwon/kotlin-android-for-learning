整个协议只有三个名词。README 里的定义值得逐字读：

> - **Thread**: A conversation between a user and the Codex agent. Each thread contains multiple turns.
> - **Turn**: One turn of the conversation, typically starting with a user message and finishing with
>   an agent message. Each turn contains multiple items.
> - **Item**: Represents user inputs and agent outputs as part of the turn, persisted and used as the
>   context for future conversations.

## thread：唯一持久的那个

thread 是**有生命周期的领域对象**，不是一个数组：

| 操作 | 方法 |
| --- | --- |
| 创建 | `thread/start` |
| 继续已有会话 | `thread/resume` |
| 分叉 | `thread/fork` |
| 读（不加载） | `thread/read` |
| 列出 / 分页 / 过滤 | `thread/list` |
| 归档 / 取消归档 / 删除 | `thread/archive` `thread/unarchive` `thread/delete` |
| 退订事件 | `thread/unsubscribe` |
| 分组 | `threadSection/*` |

几个值得注意的语义：

**加载 ≠ 存在。** `thread/list` 能列出所有存过的 thread，但它们的 `status` 默认是
`notLoaded`。只有 `start` / `resume` / `fork` 才会把它加载进内存并**自动订阅**它的事件。
`thread/read` 可以读一个没加载的 thread。

**ephemeral。** `thread/start` 和 `thread/fork` 都接受 `ephemeral: true`，
表示只在内存里、不落盘。这时返回的 `thread.path` 是 `null`，`thread.ephemeral` 是 `true`。

**fork 的边界很讲究。** 可以传 `lastTurnId` 只复制到某个 turn（含），
也可以用实验性的 `beforeTurnId` 复制到某个 turn 之前（**允许那个 turn 正在跑**）。
如果两个边界都不给、而源 thread 正在跑一个 turn，fork 会记下一个和 `turn/interrupt`
一样的中断标记——**而不是**继承一段没头没尾的半个 turn。

<Callout type="design" title="这个细节值得停一下">

「fork 一个正在进行中的会话」这种事，最容易出的 bug 是把一段残缺的历史带过去，
让新 thread 从一个模型看不懂的状态开始。

Codex 的处理是：宁可显式记一个"这里被中断了"，也不留下歧义。
**把异常状态显式化，而不是让它看起来像正常状态**——这条在整个仓库里反复出现。

</Callout>

## turn：短暂的那个

`turn/start` **立刻返回**一个 turn 对象，真正开始跑时才发 `turn/started`。
结束时发 `turn/completed`，带最终状态和 token 用量。

turn 进行中能做的事：

- `turn/interrupt` —— 停掉；
- `turn/steer` —— 往输入队列里塞新内容，下次采样带上。

`turn/start` 可以覆盖模型、cwd、沙箱策略、审批策略等等——**这些覆盖是 turn 级的**，
不改 thread 的默认设置。3.3 讲的 `TurnContext` 就是这一层的内核对应物。

## item：可展示的那个

item 是「turn 里最小的、既要给人看又要进上下文」的单元。类型包括
用户消息、agent 消息、推理、命令执行、文件改动、MCP 工具调用、计划……

事件流也是按 item 组织的：`item/started` → 若干 delta → `item/completed`。

<Callout type="tip" title="前端应该按 item 增量渲染">

不要等 `turn/completed` 再整块渲染，也不要按"消息"为单位。
协议给的粒度就是 item，按它来最省事：

```text
item/started            → 在界面上插一个新的卡片，状态 = 进行中
item/…/delta            → 往那个卡片里追加内容
item/completed          → 把卡片标成完成，带上最终数据
```

TUI 的 `history_cell` 就是这么组织的（6.3）。

</Callout>

## 和内核类型的对应

| 协议 | 内核 |
| --- | --- |
| thread | `CodexThread` / `Session`（3.2、3.3） |
| turn | `Turn` + `TurnContext`（3.3） |
| item | `ResponseItem` / `items.rs` 里的那组类型 |

中间的翻译在 `core/src/event_mapping.rs` 与
`app-server-protocol/src/protocol/event_mapping.rs`。两边不是一一对应——
**内核事件比协议事件细**，有些内核事件不会外露。

`thread/list` 是列存储，不是加载。加载是 `start` / `resume` / `fork` 这三个动作，
它们同时还会**自动订阅**该 thread 的 turn / item 事件。

`thread/read` 是个只读入口，可以带 `includeTurns` 把历史一起读出来，全程不加载。

分清「存着的」和「加载了的」，是用对这套 API 的第一步。

</Quiz>

## 一句话结论

thread 是持久的、turn 是短暂的、item 是可展示的——三者不要混用。
