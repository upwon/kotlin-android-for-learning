`codex-rs/` 下有 131 个 workspace 成员。直接看这份清单只会让人劝退——
但它们并不是平铺的，而是**分层的**。这一章给你一张能定位的坐标系。

## 顶层：四个目录

```text
codex/
├── codex-rs/     Rust 工作区，几乎所有实现都在这里
├── codex-cli/    npm 包 @openai/codex 的壳（一个 JS shim + 打包脚本）
├── sdk/          TypeScript / Python SDK
└── docs/         面向用户的文档
```

外加根目录的 `AGENTS.md`——两万字的贡献者规约，是全仓库信息密度最高的单个文件（见 10.5）。

<Callout type="success" title="这张图里最反直觉的一条">

`tui` 在**前端层**，不在内核层。它和第三方 IDE 扩展一样，是 app-server 的客户端——
只不过它把 app-server 跑在同一个进程里而已。这一点是理解整个架构的钥匙，
1.1 和 2.10 会把它讲透。

</Callout>

## 大头在哪

| crate | 行数（含测试） | 它是什么 |
| --- | --- | --- |
| `core` | ~311,000 | 对话内核：thread / turn / 工具 / 上下文 |
| `tui` | ~245,000 | 终端界面 |
| `app-server` | ~132,000 | 前端与内核之间的那层服务 |
| `exec-server` | ~40,000 | 可远程化的执行环境 |
| `core-plugins` | ~38,000 | 内置插件 |
| `app-server-protocol` | ~31,000 | 协议类型定义 |

三个大头占了全部代码的一半以上。好消息是：**它们内部也是分层的**，
而且各自有清晰的入口文件，不必整块吞下去。

## 命名规律

看到陌生 crate 名先套这几个模式，命中率很高：

- **`xxx-protocol`** —— 纯类型定义，没有业务逻辑。想知道某个子系统"能做什么"，
  读它的 protocol crate 比读实现快得多。
- **`xxx-client` / `xxx-server`** —— 一条协议的两端。
- **`xxx-mock-client`** —— 测试替身，读源码时可以跳过。
- **`ext/*`** —— 挂在扩展点上的实现（agent、goal、guardian、memories、queue、skills、web-search…）。

三件套最完整的四组：

| 协议 | 客户端 | 服务端 / 宿主 |
| --- | --- | --- |
| `app-server-protocol` | `app-server-client` | `app-server` |
| `exec-server-protocol` | （在 `exec-server/src/client`） | `exec-server` |
| `code-mode-protocol` | `code-mode` | `code-mode-host` |
| — | `cloud-tasks-client` | （Codex Web，不在本仓库） |

## 可以先跳过的

- `vendor/`、`third_party/` —— 第三方代码。
- `v8-poc` —— 名字里就写了 poc。
- `*-mock-*`、`test-binary-support`、`thread-manager-sample` —— 测试与示例支撑。
- `app-server-protocol-noop-macros` —— 为了让宏在某些编译配置下变成空实现。

## 怎么用这张图

遇到一个不认识的 crate，**先定位它在哪一层**，比查它的名字有用：

- 在**协议层** → 它没有逻辑，读类型定义就够；
- 在**执行与安全层** → 它一定和"跑外部东西"有关，重点看它的失败与降级路径；
- 在**扩展层** → 它是可选的，主链路不经过它；
- 在**基础设施层** → 大概率不用读。

## 一句话结论

看到一个陌生 crate，先问它在「协议 / 内核 / 执行 / 扩展」哪一层——位置比名字更能说明问题。
