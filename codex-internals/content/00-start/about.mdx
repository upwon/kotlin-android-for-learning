这个站是一份 **openai/codex 源码阅读笔记**，按「一次对话是怎么走完的」重新组织，
而不是按仓库目录顺序罗列。

## 为什么值得读这个仓库

市面上关于「怎么用 AI 编码工具」的材料很多，关于「一个生产级 agent 内部长什么样」的很少。
`openai/codex` 是个罕见的样本：

- 它是**真在被几百万人用**的东西，不是玩具或教学项目；
- 它把**协议、内核、工具层、三个操作系统的沙箱、终端 UI、两个 SDK** 全部开源了；
- 它的架构是**被真实约束逼出来的**——多前端、跨平台、要审批、要断点续传、要能在 CI 里跑。

换句话说，你在这里看到的每一处「为什么这么绕」，背后基本都有一个具体的、你早晚也会撞上的问题。

<Callout type="note" title="规模心里有个数">

按本站钉住的这个快照统计，`codex-rs/` 下有 **2963 个 `.rs` 文件、约 133 万行**（含测试），
分成 **131 个 workspace 成员**。其中最大的三个是 `core`（31 万行）、`tui`（24.5 万行）、
`app-server`（13 万行）。

这个体量不可能"从头读到尾"。所以本站的第一件事，是给你一张能定位的地图。

</Callout>

## 本站的裁剪原则

只讲**架构与机制**，不做 API 手册。具体地说：

| 讲 | 不讲 |
| --- | --- |
| 模块之间的边界与协议 | 每个函数的签名 |
| 某个设计为什么长这样、代价是什么 | 怎么配置某个功能（官方文档已经写了） |
| 数据在系统里怎么流动 | Rust 语法教学（附录里只给最低限度的提示） |
| 能被源码验证的结论 | 猜测与"大概是" |

每一章开头都有「**本章对应源码**」，直接跳到 GitHub 上钉住的那个 commit。
本站的立场是：**任何一句结论，你都应该能在十秒内点过去核对**。如果做不到，那是本站的问题。

## 三条推荐路线

<Callout type="tip" title="按目的选起点，别按目录顺序读">

**想接入 Codex**（写 IDE 插件、做自己的前端、用 SDK 嵌进流水线）
→ 第 2 部 app-server 从头读，然后跳到第 9 部 SDK。第 3 部以后可以先不看。

**想改内核**（加工具、改上下文策略、调 turn 逻辑）
→ 先读 1.2「一次 turn 的端到端生命周期」建立主链，再读第 3 部与第 4 部。

**为沙箱而来**（想知道怎么安全地让模型跑命令）
→ 直接第 5 部。5.1 → 5.7 是一条完整的线，中间三章是三个平台的具体实现，可按需挑。

</Callout>

## 关于快照

Codex 主干每天几十个提交。为了让正文里的路径与行号不至于两周就全废，
本站把所有源码链接**钉在一个具体的 commit** 上，页头右上角能看到它。

这意味着：你在 `main` 上看到的代码可能已经和这里写的不一样了。
遇到对不上的地方，先看 commit 是不是差太远——但架构层面的结论通常比行号活得久。

一百三十多个 crate 没有一个"自然"的阅读顺序。唯一稳定的线索是**数据流**：
用户输入怎么变成请求、请求怎么变成模型调用、模型输出怎么变成工具执行、
结果怎么回到界面。这条线走通了，任何一个 crate 你都知道它挂在哪。

至于 Rust——读懂比写出来要求低得多，附录里给了最低限度的提示。

</Quiz>
