仓库里有好几个 crate 名字里带 `protocol`，类型名也长得很像（到处都是 `Request`、
`Notification`、`Event`）。读之前先把它们**彻底分开**，能省掉很多困惑。

## A. app-server JSON-RPC：前端 ↔ 内核

- **谁定的**：Codex 自己。
- **形状**：JSON-RPC 2.0，但**省掉了 `"jsonrpc":"2.0"` 这一行**。
- **特点**：双向。除了客户端发的 137 种请求，服务端也能反过来向客户端发请求（审批、
  elicitation、取当前时间…），还有 71 种通知。
- **代码在**：`app-server-protocol`（类型）+ `app-server`（实现）。

这是第 2 部整部的主题。

## B. MCP：Codex ↔ 外部工具

- **谁定的**：Model Context Protocol，公开标准。
- **Codex 在这条协议上是双向的**：

| 角色 | crate | 用途 |
| --- | --- | --- |
| **client** | `rmcp-client` | 把外部 MCP 服务器的工具接进来给模型用（4.5） |
| **server** | `mcp-server` | 把整个 Codex 暴露成别人的工具（8.1） |

<Callout type="note" title="第三个 MCP crate">

还有个 `codex-mcp`，是前两者共用的实现部分。看到三个名字里带 mcp 的 crate 不用慌，
按"客户端 / 服务端 / 共用"分就行。

</Callout>

## C. Responses API：Codex ↔ 模型

- **谁定的**：OpenAI。
- **入口**：`core/src/client.rs`。请求组装、SSE 流式解析、重试策略都在这一层。
- **可替换**：`model-provider` / `model-provider-info` 抽象了 provider，
  本地模型（`ollama`、`lmstudio`）也走同一套（3.6）。

## 还有一条容易被误认成协议的东西

`codex-rs/protocol/`（注意：**不带前缀**）不是上面任何一条。它是**内核内部**的类型库——
`Event`、`Op`、`items`、`approvals`、`ThreadId` 这些。app-server 协议里的很多类型是从它
映射过去的（`event_mapping.rs` 就干这件事）。

一张对照表：

| crate | 是什么 | 谁读它 |
| --- | --- | --- |
| `app-server-protocol` | 前端 ↔ 内核的**对外**协议 | 前端作者、SDK 作者 |
| `protocol` | 内核**内部**的事件与类型 | 改内核的人 |
| `exec-server-protocol` | 内核 ↔ 执行环境（7.4） | 改执行层的人 |
| `code-mode-protocol` | code-mode 宿主 ↔ 运行时（4.7） | 改 code-mode 的人 |

## 为什么 A 没有直接用 B

这是个值得单独想一想的问题，2.1 会展开。简短版本：

MCP 的交互形状是「客户端问、服务端答」，加上服务端可以推一点通知。
而一个 agent 前端需要的是**双向、有状态、事件密集**：

- 审批必须是服务端向客户端发起的**请求**（要等一个答复），不是通知；
- thread 是长期存在、可 resume / fork / archive 的**有状态资源**；
- 一次 turn 会推出几十上百条细粒度事件（item 增删改、逐字 delta、token 用量）。

这三件事 MCP 都表达不了或表达得很别扭。于是 Codex 借了它的形（JSON-RPC over stdio），
没借它的语义。

- **A 错**：IDE 扩展要读的是 `app-server-protocol`。不带前缀的 `protocol` 是内核内部类型。

- **C 对**：README 里明确写了这一行在传输时被省掉。
- **D 错**：provider 被隔离在 `client.rs` / `model-provider*` 那一层，turn 循环不感知。

## 一句话结论

看到 “protocol” 先问是哪一条——这三条的类型名很像，但完全不是一回事。
