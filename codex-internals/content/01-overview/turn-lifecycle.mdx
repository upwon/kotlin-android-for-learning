## 主循环长什么样

先看内核里那个循环的原文描述，它把整件事说得非常干净：

> Takes initial turn input and runs a loop where, at each sampling request,
> the model replies with either: requested function calls, or an assistant message.
>
> - If the model requests a function call, we execute it and send the output back to the model
>   in the next sampling request.
> - If the model sends only an assistant message, we record it in the conversation history
>   and consider the turn complete.

<Source path="codex-rs/core/src/session/turn.rs" lines="139-153" />

**一个 turn = 反复采样，直到模型不再要求调工具为止。** 就这么简单。
剩下的一百三十万行，做的都是「怎么把这件事做对、做安全、做得能观测」。

### ① 前端把输入变成请求

`turn/start`，带上 `threadId` 和用户输入。可选字段能覆盖模型、cwd、沙箱策略、审批策略等等。
这个调用**立刻返回** turn 对象——真正开始跑的时候，服务端才发 `turn/started` 通知。

### ② app-server 找到 thread，起一个 turn

`turn_processor` 把请求交给已加载的 thread。注意 thread 必须先通过
`thread/start` / `thread/resume` / `thread/fork` 加载——协议里 thread 是有状态的（见 2.4）。

### ③ core 组装 prompt，调模型

内核在这里做的事情比看上去多：

- 从 `context_manager` 取出历史，按 token 预算裁剪（3.4）；
- 拼上系统提示、`AGENTS.md`、环境信息、命中的 skills（3.9）；
- 算出**这一轮**模型可见的工具列表（4.1，它是每轮重算的）；
- 调 `client.rs` 发请求，拿回 SSE 流。

流式片段被规整成内核事件，再由 `event_mapping` 翻译成协议通知，一路推回前端——
所以你在界面上看到的逐字输出，中间经过了两次翻译。

### ④ 工具调用：路由 → 判定 → 执行

模型要求调工具时：

1. `router` 找到 handler，`orchestrator` 决定顺序与能不能并行（4.2）；
2. `safety.rs` 把审批策略、沙箱策略、execpolicy 判定、历史批准合到一起，
   给出四选一的结论：**直接跑 / 进沙箱跑 / 问用户 / 拒绝**（5.7）；
3. 需要问用户时，服务端向客户端发一个**反向请求**（2.8）——这是整条链上唯一一个
   方向反过来的地方，也是 app-server 不能用 MCP 的核心原因；
4. 批准后进沙箱执行（第 5 部）；
5. 输出回灌进上下文，回到 ③ 再采样一次。

### ⑤ 全程落盘

turn 进行中，rollout 一直在写。这也是 `codex resume` / `codex fork` 能工作的原因——
**会话的真相在磁盘上，内存里的只是缓存**（3.8）。

## 三个插进来的东西

| 机制 | 插在哪 | 干什么 |
| --- | --- | --- |
| **中断** `turn/interrupt` | ③ 与 ④ 之间的任意点 | 停掉当前采样与在跑的工具，turn 以 interrupted 结束 |
| **steer** `turn/steer` | ③ 采样之前 | turn 还在跑，往输入队列里塞新内容，下一次采样时带上 |
| **compact** | ③ 组装 prompt 之前 | 上下文快满了，先压缩历史再采样（3.5） |

<Callout type="tip" title="steer 和「等它跑完再说」不一样">

`run_turn` 里有个细节：pending input 的 drain 时机是被**刻意推迟**的——turn 刚开始时
先让新鲜输入被采样，自动 compact 之后也要先让模型/工具续上，才允许 steer 插进来。
不然用户中途补的一句话可能会打断一次正在收尾的工具调用。

</Callout>

## 一次 turn 会调几次模型

取决于模型要调几轮工具。一次"帮我改个 bug"的对话，典型是：

```text
采样 1 → 要求 shell(rg "foo")        → 执行 → 回灌
采样 2 → 要求 shell(cat src/a.rs)    → 执行 → 回灌
采样 3 → 要求 apply_patch(...)       → 审批 → 执行 → 回灌
采样 4 → 只回了一段助手消息            → turn 结束
```

四次采样、三次工具执行、一次审批往返、一路事件推送、全程落盘——
这就是那条你每天在用、平时看不见的链。

审批在这个协议里是**服务端发起的请求**：`item/commandExecution/requestApproval`
这类 `ServerRequest` 从服务端发给客户端，客户端的响应就是判定结果。

这也是为什么 app-server 不能直接用 MCP——MCP 的形状是客户端问、服务端答，
反向请求这件事它表达不了（2.1、2.8）。

</Quiz>
